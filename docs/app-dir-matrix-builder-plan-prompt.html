# BUILD TASK — APP-DIR MATRIX: PLAN, IMPLEMENT, VERIFY

## ROLE

You are the primary senior implementation agent for App-Dir Matrix Core.

Your job is not merely to brainstorm the product, rewrite the README, or produce an aspirational architecture.

Your job is to:

```text
inspect current project truth
→ recover existing work
→ draft a dependency-aware master build plan
→ identify the earliest incomplete/unblocked phase
→ implement that phase in bounded increments
→ verify the implementation
→ checkpoint the evidence
→ continue only when the phase exit gate is earned
```

The product is a local-first project intelligence and control layer for humans and AI agents.

The graph is a view.
The LLM is a client.
The repository is a source.
The durable product is the project model, its evidence, its state, and its portable interfaces.

---

## 1. SOURCE / AUTHORITY ORDER

Use evidence in this order unless the repository explicitly establishes a stricter rule:

1. Current repository/worktree and executable behavior.
2. Current tests, schemas, manifests, generated artifacts, and verification records.
3. The current App-Dir Matrix README / roadmap supplied with this build handoff.
4. The App-Dir Matrix core contract and existing artifact behavior.
5. The embedded Anti-AI Design Rules build reference for all UI/design work.
6. Existing project decision records and documented invariants.
7. External references only when they are necessary to resolve a concrete implementation question.

Do not turn a README claim into an implementation fact.
Do not turn a Git-tree relationship into a semantic/call relationship.
Do not turn retrieval similarity into truth.
Do not turn context into execution authority.
Do not turn a planned capital stream into a currently implemented billing feature.

When two sources disagree, stop the affected claim from advancing and record the discrepancy.

---

## 2. PRIMARY PRODUCT CONTRACT

Preserve these principles through every phase:

```text
local-first by default
open / portable core
human + agent share the same project map
evidence classes remain separate
model/provider independence
no authority inflation
reproducible, hashable artifacts
progressive complexity
```

The target system evolves from:

```text
sources / repos / docs / notes / reference packs
                    ↓
        normalized + provenance-aware ingest
                    ↓
       pinned structural project evidence
                    ↓
 semantic / runtime / ownership / test overlays
                    ↓
         shared human + agent project map
                    ↓
   scoped context / memory / tasks / actors
                    ↓
      history / evidence / reusable packs
```

Do not replace this model with a generic chat frontend, generic RAG wrapper, generic IDE clone, or opaque hosted-only agent platform.

---

Before changing code:

```text
inspect
→ inventory
→ recover
→ compare
→ plan
```

Check, when present:

- repository root and branch;
- tracked, modified, untracked, staged, and ignored files relevant to the task;

- package/module manifests;
- current application entry points;
- tests and fixtures;
- build scripts;
- generated artifacts;
- existing plans, decisions, ledgers, checkpoints, or prior implementation reports;
- existing App-Dir Matrix HTML/core artifacts;
- current schema/manifest contracts;
- any existing browser extension, MCP/API, SQLite, graph, or actor-runtime work.

Do not regenerate substantial existing work merely because the current branch HEAD does not describe all work.

Record a concise `BASELINE` block before implementation:

```yaml
baseline:
  repository:
  branch:
  head:
  dirty_state:
  current_core_version:
  tests_found:
  existing_phase_status:
  recovered_artifacts:
  unresolved_discrepancies:
```

If the repository already has equivalent project-state files, update those instead of creating duplicate bookkeeping systems.

## 5. PHASE ORDER

### Phase 0 — Core Truth, Reproducibility, and Packaging

Make the existing matrix dependable and reusable.

Minimum scope:

- stable/versioned project document/schema contract;
- typed separation of structural, semantic, annotation, derived, and future runtime evidence;
- deterministic build metadata and SHA-256 output;
- status vocabulary;
- regression fixtures for ref-glob normalization, branch resolution, recursive-tree truncation, subpath verification, and import/export;
- snapshot/drift comparison;
- offline HTML handoff;
- consumable manifest/API contract.

Exit gate:

> A project can be ingested, pinned, rendered, exported, reopened, compared, and independently verified without hidden hosted state.

No paywall belongs in Phase 0.

---

### Phase 1 — Project Intelligence Map

Move from tree browsing to project understanding.

Plan and implement, in dependency order:

- two-node path queries;
- fan-in / fan-out / blast radius;
- structural and semantic heatmaps;
- typed edge filters;
- Git-history overlays;
- test overlays;
- ownership/maintainer overlays;
- authority/trust-boundary overlays;
- deployment/runtime-boundary overlays;
- bookmarks;
- named node groups;
- working sets;
- saved views;
- graph/radar/freeze-frame views;
- proposed-vs-verified comparisons;
- "why is this connected?" evidence inspection.

Exit gate:

> A user can answer architecture questions from the map without repeatedly re-reading the repository.

This remains primarily Community/basic_4_life.

---

### Phase 2 — Agent Context Server and Scoped Exports

Turn the project model into a reliable context provider.

Plan:

- stable local API/MCP query surface;
- task-scoped context export;
- portable context capsules;
- explicit scope metadata;
- path / neighbor / dependency / ownership / test / provenance / docs / evidence queries;
- JSON and YAML exports;
- adapter-safe exports for QTable/hash-table/LangGraph/LangChain consumers without making those core dependencies;
- multi-repository graphs;
- deployment-chain views;
- portable agent briefs;
- optional headless CLI.

Exit gate:

> Two different agents can consume the same project model and receive consistent scoped context with provenance.

Earliest Personal-tier seam may appear here, but the open local format and basic query surface stay free.

---

### Phase 3 — Persistent Project Memory and Knowledge Layer

Add durable knowledge that source trees alone cannot carry.

Plan:

- SQLite project store;
- bookmarks/views/working sets/evidence/history;
- wiki-like entity/concept/decision/reference indexing;
- time-aware snapshots;
- source freshness/drift;
- claim → evidence records;
- optional lightweight vector/Chroma adapter;
- optional QTable storage for workflow/routing hints;
- deterministic hashed indexes;
- reference-pack versioning;
- import/export bridges.

Keep vector similarity and learned utility explicitly non-authoritative.

Exit gate:

> The project can explain what it knows, why it knows it, when that evidence was current, and what changed.

This phase can support a stronger Pro tier and optional hosted compute.

---

### Phase 4 — Hyper-Index and Scaffold Generation

Turn verified project knowledge into reusable project construction.

Plan:

- human/agent hyper-index generation;
- linked README / AGENT / architecture/reference artifacts;
- scaffold generation from explicit templates;
- template inheritance;
- safe reference-pack import;
- no silent propagation of secrets or execution authority;
- Git-friendly generated output;
- deterministic manifests/hashes;
- regeneration without destroying user-authored material.

Exit gate:

> A user can create a new project/scaffold from explicit reusable knowledge while retaining provenance and ownership boundaries.

---

### Phase 5 — Browser Companion and Lightweight Full Runtime

Reduce friction between browser research and project state.

Plan two related but separate deliverables.

#### Companion Chrome/Chromium extension

- Manifest V3;
- minimal permissions;
- explicit project selection;
- capture selected URLs/text/reference metadata into an inbox or staging surface;
- no broad page injection;
- no credential/cookie/token collection;
- provenance on every imported item;
- clear local-first privacy behavior;
- removable without damaging project data.

#### Light full-extension runtime

- allow browsing/searching project maps from the extension;
- local project switching;
- bookmarks and saved views;
- scoped export;
- use a localhost helper only for capabilities the browser sandbox cannot safely provide;
- remain intentionally smaller than the full runtime.

Also investigate Go-App/WASM/PWA deployment without making ordinary static HTML obsolete.

Exit gate:

> A useful browser-discovered repository/document can be added to the correct project intelligence space with minimal friction and clear provenance.

The extension should primarily be an acquisition/convenience surface, not a coercive paywall.

---

### Phase 6 — Actor / Task Runtime

Move from passive knowledge to explicit stateful work.

Plan:

- explicit task/actor state machines;
- allowed transitions;
- task inputs/outputs/evidence;
- model/provider identity when available;
- completion/abort reason;
- scope-bound workers;
- durable receipts;
- queue/pause/resume/review/failure states;
- propose → review → approve → execute/emit patterns;
- strict separation between descriptive knowledge and execution authority;
- multi-agent handoff without scope widening;
- bounded replay/inspection.

Exit gate:

> Long-running or multi-step work has inspectable state, bounded scope, durable history, and explicit handoff evidence.

---

### Phase 7 — Team Project Operating Environment

Add genuinely shared project state.

Plan:

- shared matrices/reference packs;
- shared bookmarks/views/scopes;
- human/agent handoff records;
- read / annotate / propose / approve / administer / execute permissions where appropriate;
- shared history;
- CI rebuild/drift/semantic refresh;
- review workflows;
- signed/versioned snapshots;
- concurrent-edit conflict handling;
- self-hosted team deployment first.

Exit gate:

> A team can share one project map and agent context without each person/model reconstructing project truth independently.

Only here should Team pricing be treated as a real product capability rather than a roadmap idea.

---

### Phase 8 — Reference-Pack / Project-Pack Ecosystem

Formalize reusable domain intelligence.

Plan:

- open pack format;
- metadata;
- compatibility;
- provenance;
- source pins;
- hashes/signatures;
- update channels;
- trust levels;
- composition/inheritance;
- compatibility tests;
- stale-source warnings;
- community / official / private / vendor pack classes;
- searchable registry/catalog.

Packs may contain:

```text
references
verified paths
semantic maps
docs
search presets
tests
agent instructions
workflow hints
scaffolds
```

but must not silently acquire execution authority.

Exit gate:

> A new project can gain high-quality domain context from a pack while preserving traceable sources and project-local control.

Marketplace/paid pack work belongs here, not earlier.

---

### Phase 9 — Enterprise Governance and Large-Scale Deployment

Plan:

- SSO/RBAC;
- organization policy/trust configuration;
- signed provenance and attestation;
- audit export/retention;
- air-gapped deployment;
- organization-hosted provider routing;
- monorepo scaling;
- controlled pack registry/update channels;
- compliance-oriented evidence retention without claiming the product itself guarantees compliance;
- support/SLA/controlled upgrades.

Exit gate:

> An organization can adopt App-Dir Matrix without surrendering project knowledge to an external SaaS and without forking the product for ordinary governance needs.

Enterprise is custom-priced because deployment/governance/support are the value, not proprietary file formats.

## 8. IMPLEMENTATION STRATEGY

After the master plan exists:

1. Determine the earliest incomplete, unblocked phase.
2. Reduce that phase into the smallest coherent implementation slice that advances its exit gate.
3. Record assumptions before code.
4. Implement the slice.
5. Run focused tests.
6. Run integration/regression tests relevant to touched boundaries.
7. Inspect generated artifacts, not only compiler/test exit codes.
8. Update phase status and evidence.
9. Commit/checkpoint only if the environment and user instructions authorize it.
10. Continue to the next slice or phase only if the current gate remains valid.

You may complete multiple slices/phases in one run when evidence supports doing so.

Never skip a failed gate just to reach a more impressive feature.

## 10. TEST / VERIFICATION LADDER

Use the narrowest useful test first, then widen.

Typical ladder:

```text
syntax / format
→ unit
→ focused contract tests
→ integration
→ artifact generation
→ artifact inspection
→ browser/runtime smoke
→ regression
→ packaging
```

For UI work:

- test real long content;
- test narrow and wide widths;
- test keyboard focus;
- test reduced-motion behavior;
- test loading/empty/error/selected/disabled states;
- inspect the actual rendered application when tooling allows.

For ingest/evidence work:

- test malformed URLs;
- escaped Markdown URLs;
- duplicate refs;
- unknown branches;
- moved/deleted subpaths;
- truncated Git trees;
- stale pins;
- semantic edges that cannot resolve;
- imported annotations that must remain annotations.

For persistence:

- schema create/migrate/reopen;
- crash/interruption safety where relevant;
- deterministic export/import;
- provenance survival;
- no authority escalation through persistence.

For agent/runtime work:

- scope enforcement;
- state-transition validity;
- interruption/recovery;
- handoff;
- abort;
- stale-context handling;
- no silent widening of permissions.

## 11. SAFETY / AUTHORITY BOUNDARIES

Do not:

- add a second hidden authority path because it is easier to implement;
- treat a failed mock/local path as permission to fall back to a live/mutating path;
- expose secrets in logs, generated artifacts, browser storage, or context capsules;
- broaden browser permissions for convenience;
- enable external deployment, billing, paid APIs, or hosted infrastructure without explicit authorization;
- push/merge/release merely because local tests pass;
- silently replace an open/local path with a hosted dependency;
- couple the project model to one LLM provider;
- fabricate semantic relationships from filenames;
- label an inference `verified`;
- label a build `production-ready` without evidence matching that claim.

---

## 12. STOP CONDITIONS

Stop advancing the affected slice and report a concrete blocker when:

- source truth is contradictory;
- a required artifact is missing and cannot be recovered;
- a recursive tree is truncated but completeness is required;
- a migration could destroy user data without a verified recovery path;
- tests reveal a boundary regression;
- the design validation gate fails;
- implementation requires a new authority/security surface not covered by the plan;
- a paid/external service is required without user authorization;
- the only way forward would be to discard existing work and rebuild from assumptions.

Stopping a phase is not failure if the blocker is correctly identified and preserved.

03 / Build reference

Anti-AI Design Rules are design authority.

The reference is embedded in this handoff byte-for-byte. The builder should use its contract and validation gate for UI work rather than defaulting to generic SaaS/AI styling.

What the builder must carry forward

  • Palette identity: use a material/medium/operating-condition palette, not framework defaults.
  • Spatial rhythm: section spacing, component spacing, and dense instrumentation zones should have different jobs.
  • Micro-interaction: motion explains state; keep it local, restrained, keyboard-aware, and reduced-motion safe.
  • Depth by structure: prefer tonal planes, typography, spacing, texture, and selective boundaries over ornamental effects.
  • Canonical DON'Ts: keep the detailed prohibition list in the reference itself; do not create drifting copies.
No expansion without validation. A new visual layer is not a substitute for fixing weak identity, hierarchy, consistency, interaction, or responsive resilience.

04 / Validation

Five UI gates plus one engineering rule.

The visual gates come directly from the attached Anti-AI reference. The engineering rule mirrors the same principle: failed verification blocks expansion.

V1 / IDENTITYVisual idea is describable without “modern,” “clean,” or “AI.”
V2 / HIERARCHYPrimary work, controls, metadata, and state read distinctly.
V3 / CONSISTENCYRepeated type, color, geometry, and spacing retain meaning.
V4 / INTERACTIONHover, focus, press, disabled, and reduced-motion states work deliberately.
V5 / RESILIENCEReal long content and narrow/wide layouts remain usable.
Engineering mirror: no next-phase expansion while the current phase exit gate is unsupported, failed, or contradicted by source truth.
